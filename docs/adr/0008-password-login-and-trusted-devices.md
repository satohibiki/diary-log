# ADR-0008: パスワードでのログインと、端末の確認

- **Status**: 採用
- **Date**: 2026-11-22

## 背景

001 では、漏えいのリスクを抑えるため、ログインを ID とパスキーだけにし、パスワードを扱わないと定めた(001 FR-002、
ADR-0003)。しかし、パスキーに対応していない端末やブラウザでは、ログインも利用もできない。

004-id-password-login で、ID とパスワードでのログインを標準の方法とし、パスキーでのログインも残すことにした。
パスワードの漏えいに備え、初めて使う端末では、メールのワンタイムパスワード(OTP)も求める(004 の Clarifications)。
この ADR は、ADR-0003 の「パスワードを扱わない」前提を置き換える。

## 決定

- **ハッシュ**: Node.js 標準の `crypto.scrypt` を使う。N=2^15、r=8、p=3(1回あたり約32MB)、ソルトはユーザーごとに
  16バイトの乱数、出力は32バイト。保存は `scrypt$<log2 N>$<r>$<p>$<salt>$<hash>`(base64url)の自己記述の形式にし、
  将来パラメーターを上げても古いハッシュを検証できるようにする。比較は定数時間で行う。
- **条件**: Unicode の NFKC で正規化してから、長さ(コードポイント数で12〜128)を判定してハッシュする。組み合わせの強制と
  定期的な変更はしない。よく使われるパスワードと、ID を含むパスワードを拒否する。
- **よく使われるパスワードの一覧**: SecLists(MIT License、Copyright (c) 2018 Daniel Miessler)の
  `Passwords/Common-Credentials/xato-net-10-million-passwords-1000000.txt` から、NFKC と小文字化のあとで12コードポイント
  以上のものだけを取り出し、`apps/server/src/auth/common-passwords.txt` に置く(`scripts/build-common-passwords.ts`)。
  外部のサービスには問い合わせない(憲章 III)。
- **ID の列挙の防止**: ID が存在しない場合とパスワードを持たない場合も、固定のダミーのハッシュに対して同じ計算を行い、
  同じ 401 を返す。
- **暗号化しない**: `users.password_hash` は復元できない形のため、憲章 II の暗号化(日記データとメールアドレス)の対象外
  とする。
- **端末の確認**: Cookie `__Host-device`(HttpOnly、Secure、SameSite=Strict、90日)に乱数のトークンを置き、DB の
  `trusted_devices` にはトークンのハッシュとユーザーの組、最後の利用日時、有効期限だけを保存する。パスワードが正しくても
  未確認の端末では、10分の `device_check` のセッションにとどめ、メールの OTP を確かめてから通常のセッションにする。
  最後の利用から90日で失効し、パスワードの設定と変更、復旧の完了、退会で、そのユーザーの全端末を失効させる。
  アカウントの作成と復旧の完了では、OTP を確かめたその端末を確認済みにする。パスキーでのログインには確認を求めない。

## 検討した代替案

- **Argon2id**: 推奨の第一候補だが、ネイティブの依存(`argon2`)が増える。標準の scrypt で十分なため不採用(憲章 VI)。
- **bcrypt**: 72バイトの上限があり、長い日本語のパスフレーズを受け付けられない。
- **PBKDF2**: メモリを使わず、GPU による推測に弱い。
- **pepper(サーバーの秘密鍵との HMAC)**: DB だけの漏えいには有効だが、鍵の入れ替えの運用が要る。今回は入れず、
  必要になったら新しい ADR で検討する。
- **外部の漏えいパスワードの照会(k-匿名性)**: パスワードのハッシュの一部を外部へ送ることになり、憲章 III に反する。
- **端末の指紋(User-Agent、IP など)**: 変わりやすく、個人を特定しうる情報を保存することになる。
- **毎回の OTP**: 利用者の判断により、初めての端末だけにした。

## 影響

- パスワードを扱うため、総当たりやリスト型攻撃の対象になる。回数制限、よく使われるパスワードの拒否、初めての端末での
  OTP、変更と新しい端末の通知で抑える。メールの乗っ取りが最大のリスクである点は ADR-0003 と変わらない。
- scrypt の計算は1回あたり約32MBのメモリを使う。ログインの回数制限を、比較の前に消費して負荷を抑える。
- パスキーでの登録の経路はなくなる。列挙型 `challenge_purpose` の `register` は使わなくなるが、削除しない。
- `common-passwords.txt` は約4.6万行、約0.7MB で、サーバーだけが読み込む(画面には配信しない)。
