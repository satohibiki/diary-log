# Research: 手書きの絵日記帳風 UI

## 1. 手書き風の書体

- **Decision**: Klee One(Fontworks、SIL Open Font License 1.1)の Regular(400)を使う。npm パッケージ `@fontsource/klee-one` の `400.css` を Web アプリから読み込み、Vite のビルドで書体ファイルをアプリと同じオリジンから配信する。
- **Rationale**:
  - 鉛筆やペンで丁寧に書いたような楷書体で、仕様の「ていねいなペン字風」(Q2: B)に合い、400文字でも読みやすい。
  - ひらがな、カタカナ、JIS 第1・第2水準の漢字を含む。
  - OFL のため、自サービスからの配信と再配布が許される。
  - `@fontsource` は Google Fonts と同じ方式で、文字の範囲ごとに 124 個の woff2 ファイルに分割されている(`unicode-range`)。ブラウザは表示する文字を含むファイルだけを取得する。
  - 一般的な日記の文章で必要になるのは約15ファイル、約280KB で、SC-004(2秒以内)を満たせる見込み。
  - CSP の `font-src 'self'` のまま使えるため、外部サービスへの通信が発生しない(FR-011、SC-006、憲章 III)。
- **Alternatives considered**:
  - **Google Fonts から読み込む**: 閲覧のたびに利用者の IP アドレスなどが Google に送られ、憲章 III(プライバシー)と CSP に反するため不採用。
  - **Zen Kurenaido(筆ペン風)、Yomogi(くだけた手書き風)**: 雰囲気が「ていねいなペン字」から離れ、長文が読みにくいため不採用。
  - **書体ファイル全体(約1.9MB)を1つで配信する**: 初回の表示が遅くなるため不採用。
  - **太字(600)も入れる**: 見出しは使わない(日付欄も通常の太さで足りる)ため、YAGNI により入れない。

## 2. 書体の読み込みと代わりの書体

- **Decision**: `font-display: swap`(パッケージの既定)を使う。代わりの書体には、各端末の標準の日本語書体(`'Hiragino Maru Gothic ProN', 'Yu Gothic', 'Noto Sans CJK JP', sans-serif`)を指定する。行の高さは書体に依存しない固定の値にする。
- **Rationale**:
  - 書体の読み込み中も、文章は代わりの書体で先に表示される(US3-3)。
  - 行の高さを固定すると、書体が切り替わっても罫線と行の位置が変わらない(Edge Cases)。
  - Klee One にない文字(絵文字など)は、ブラウザが代わりの書体で表示する(FR-012)。
- **憲章 VIII との関係**: 書体の切り替えは、仕様で求められた表示の振る舞い(US3-3、FR-012)である。エラーを隠す代替処理ではない。書体の読み込みに失敗しても、データの保存や表示の失敗は起きない。

## 3. 横書きの罫線と文字の位置合わせ

- **Decision**: 文章欄(記入時の `textarea`、表示時の段落)に共通の CSS クラスを当て、次のように描く。
  - 行の高さ: 固定の `--rule-gap`(例: `2rem`)。`line-height` と罫線の間隔に同じ変数を使う(DRY)。
  - 罫線: 背景のグラデーションを2層重ねて点線を描く。
    1. 各行の下端に1pxの線を引く縦方向のグラデーション。`background-size: 100% var(--rule-gap)` で繰り返す。
    2. その上に、紙の色を4px周期で重ねる横方向のグラデーション。線を点線に切る。
  - 上端の余白: `padding-top` を `0` にし、背景の起点を内容の領域にそろえる(`background-origin: content-box`)。
  - 罫線の位置: 文字は行の中で上下中央に置かれるため、そのままでは文字の下端が罫線より上に浮く。`--rule-offset` で罫線の位置だけを文字の下端に合わせ、行の間隔は変えない(SC-001 の1割以内)。
- **Rationale**:
  - CSP の `img-src 'self' blob:` では `data:` の SVG を背景に使えないため、CSS のグラデーションだけで描く。
  - `line-height` と罫線の間隔が同じ変数のため、何行に折り返しても、拡大しても位置がずれない(SC-001)。
  - 記入画面と表示画面で同じクラスを使うと、折り返し位置と見た目が一致する(US2-1)。
- **Alternatives considered**:
  - **1行ずつ要素を並べる**: `textarea` の中では行ごとに要素を作れず、記入と表示で作りが分かれるため不採用。
  - **`text-decoration: underline`**: 文字のない部分に線が引かれず、空の行を表せないため不採用。
  - **SVG の背景画像**: CSP の変更が必要になるため不採用。

## 4. 行数の自動調整(最初は8行、文章に合わせて増える)

- **Decision**:
  - 文章欄の最小の高さを `8 × --rule-gap` にする。
  - 記入画面では、入力のたびに `textarea` の高さを内容の高さ(`scrollHeight`)に合わせる。高さは `--rule-gap` の倍数に切り上げる。
  - 表示画面の段落は、内容に合わせて自然に伸びる。
- **Rationale**:
  - Q1: A(最初8行、増える)を満たし、すべての文章が見えたまま入力を続けられる(US1-5)。
  - CSS の `field-sizing: content` は Firefox の最新安定版での対応が確認できないため、使わない。代わりに数行の処理で高さを合わせる。
- **Alternatives considered**: 文章欄の中でスクロールさせる案は、US1-5(すべての文章が見える)に反するため不採用。

## 5. 日付欄と天気欄

- **Decision**:
  - **日付欄**:
    - 「〇月 〇日(〇)」の文字列を、純粋な関数 `formatDiaryDay(date)` で作る。年を含む既存の `formatJapaneseDate` と同じファイルに置き、曜日の計算は共通にする(DRY)。
    - 記入画面では、ネイティブの `<input type="date">`(ラベル「日付」)を日付欄の中に重ねる。見た目は透明にし、整形した文字列を表示する。
    - 欄を押すと `showPicker()` で日付の選択を開く。キーボードでは、ネイティブの日付の入力欄をそのまま操作できる。
  - **天気欄**:
    - 日付欄と同じ行の右隣に、見出し「天気」付きのラジオボタン4つを手書き風の書体で並べる(FR-004)。
    - 表示画面では、選んだ天気の名前とアイコンを表示する。
  - **年**: ページの外の見出し(例: 「2026年の絵日記」)に表示する(FR-003)。
- **Rationale**:
  - ネイティブの入力欄を残すと、日付の制約(`max`)、キーボード操作、読み上げが既存のまま使える(FR-005、FR-018)。
  - 既存のテストのラベル(「日付」「晴れ」「文章」など)も変わらない。
- **Alternatives considered**: 独自の日付選択の部品を作る案は、アクセシビリティの作り込みが大きく、KISS に反するため不採用。

## 6. ページ(カード)の見た目と配色

- **Decision**:
  - **カード**: 角の丸い薄い灰色(`#e6e6e6` 前後)のカードの内側に、2pxの黒い枠線の長方形を置く。虹色の縁取りは入れない(Q3: A)。
  - **絵の枠**: 縦横比 4:3。画像は `object-fit: contain` で枠に収める。
  - **ダークモード**: ページの配色は、ライトとダークで切り替わる既存の色の変数を使わない。ページ専用の固定の色を使う。
  - **コントラスト**: 文字 `#222` と紙 `#e6e6e6` で約13:1(FR-014 の 4.5:1 以上)。
- **Rationale**: 参考画像の見た目に近く、ダークモードでも紙らしい明るさを保てる(Edge Cases)。

## 7. 共通の部品(DRY)

- **Decision**:
  - 新しい部品 `DiaryPage` を作り、ページの枠、絵の枠、日付と天気の行、罫線の文章欄の配置を1か所で定める。
  - 記入画面(`DiaryEditor`)と表示(`DiaryCard`)の両方で使う。各欄の中身(入力欄か表示か)は、呼び出し側から渡す。
  - 縦書き用の `VerticalPage` と、縦書きの CSS(`.manuscript`、`.vertical-text`)は削除する。
- **Rationale**: 記入画面と表示画面のページ構成(FR-001)を1か所で定義でき、見た目のずれを防げる(憲章 VII)。

## 8. 脅威と対策(憲章 I)

| 対象 | 脅威 | 対策 |
|---|---|---|
| 書体ファイル | 第三者のサーバーからの読み込みによる閲覧情報の漏えい | 自サービスから配信し、CSP の `font-src 'self'` を維持する。テストで外部への通信がないことを確かめる(SC-006) |
| 書体ファイル | 改ざんされた依存関係 | `package-lock.json` の整合性ハッシュと `npm audit` を品質ゲートで確認する |
| 文章の表示 | スクリプトの注入 | これまでどおり文章は文字としてのみ表示し、HTML として解釈しない |

扱うデータ(画像、文章、日付、天気)と保存の方法は 001 から変わらない。

## 9. 既存のテストの変更(憲章 V)

- `e2e/vertical-writing.spec.ts` と `apps/web/tests/diary-editor.test.tsx` の縦書きの確認は、仕様の変更(001 の FR-010 を 002 の FR-006 で置き換え)により、横書きと罫線の確認に置き換える。
- 置き換えの理由は、tasks.md とコミットのメッセージに記録する。
