# Research: 「書く」で開く絵日記の日付を今日にする

**Feature**: [spec.md](./spec.md) | **Date**: 2026-11-22

## 1. 不具合の原因(調査結果)

2026-11-22 に「書く」(`/diaries/new`)を開くと、日付欄に「11月 8日(日)」が表示された。原因は次の3つである。

1. **新規の書きかけが1件だけ**: `draft-store.ts` は、新規の書きかけを日付に関係なく `"<user>:new"` の1つのキーで保持する。`DiaryEditor.tsx` は、このキーに書きかけがあると `setDate(draft.date)` で日付を書きかけの日付に置き換える(`DiaryEditor.tsx:44-49`)。
2. **開いただけで保持する**: 入力の 500ms 後に書きかけを保持する処理は、`loaded` が真になった時点で一度動く。そのため、何も入力しなくても、開いた日の日付が書きかけとして残る。11月8日に開いた画面の日付が、以後の「書く」に残り続けた。
3. **同じ画面のまま移動すると日付が変わらない**: `/diaries/new?date=2026-11-15` から「書く」(`/diaries/new`)へ移っても、`DiaryEditor` は作り直されない。`useState` の初期値は最初の1回しか使われないため、日付は 11月15日のまま残る。

また、既存の単体テスト `restores a draft saved before the tab was closed` は、別の日付(2026-11-03)の書きかけが「書く」で戻ることを確かめている。このテストは不具合の動きを正しいものとして固定していた。

## 2. 書きかけの分け方

- **Decision**: 新規の書きかけを、利用者と日付の組ごとに保持する。キーは `"<user>:new:<YYYY-MM-DD>"` とする。編集の書きかけのキー `"<user>:<YYYY-MM-DD>"` は変えない。
- **Rationale**: 開いた画面の日付の書きかけだけを戻せば、FR-001〜FR-003 を同時に満たせる。キーの形を変えるだけで、IndexedDB のデータベースやオブジェクトストアは変えなくてよい(バージョンを上げない)。
- **Alternatives considered**:
  - 書きかけは1件のまま、日付だけ今日に置き換える: 11月8日に書いた文章が11月22日の絵日記に入る(US1-2 に反する)。
  - 書きかけの日付と開いた日付が違ったら書きかけを捨てる: 書いた内容が失われる(憲章 IV に反する)。
  - 編集の書きかけと同じキー `"<user>:<date>"` を使う: 同じ日付で「新規」と「編集」の書きかけを区別できなくなる。

## 3. 空の書きかけを保持しない

- **Decision**: 文章が空白のみ、天気が未選択、絵がない状態を「空」とし、新規の書きかけでは保持しない。保持の代わりに、その日付のキーを消す。判定は `draft-store.ts` の `isEmptyDraft` の1か所で行う(憲章 VII)。
- **Rationale**: 開いただけで書きかけが残る原因2をなくし、FR-006 の案内に空の書きかけが出ないようにする。入力を全部消したときに、古い書きかけが残らないよう、保持の代わりに消す。
- **Alternatives considered**: 利用者が一度でも入力したかを覚えておく: 状態が増える。内容で判定すれば十分である。
- **対象外**: 編集の書きかけは、もとの絵日記の内容が入るため空にならない。動きを変えない。

## 4. 記入画面の日付の決め方

- **Decision**: 新規の記入画面の日付は、URL の `date` が正しい形式で今日以前ならその日付、それ以外は今日とする。書きかけの日付で置き換えない。形式の判定は `packages/shared` の `diaryDateSchema` を使う(憲章 I: URL パラメーターの検証、憲章 VII)。
- **Rationale**: FR-001、FR-002。日付の決め方を1つの純粋な関数(`initialDiaryDate(param, today)`)にまとめ、単体テストで確かめる。
- **不正な値の扱い**: 今日の日付で開く(spec の Edge Cases に定めたフォールバック)。利用者への通知はしない。URL を手で書き換えた場合にしか起きず、日付欄に今日の日付が表示されるので、利用者は日付を確認できる。

## 5. 同じ画面のまま「書く」を押したとき

- **Decision**: ルートの定義で、新規の記入画面に URL ごとの `key`(`location.key`)を付けて、移動のたびに `DiaryEditor` を作り直す。
- **Rationale**: 原因3を最小の変更でなくせる。状態を URL に合わせて直す `useEffect` を足すより単純である。
- **Alternatives considered**: `date` の変更を `useEffect` で状態に反映する: 書きかけの読み込みと保持の処理と順序が絡み合う。

## 6. 記入画面で日付を変えたとき

- **Decision**: 日付を変えたら、画面の内容を変更後の日付の書きかけとして保持し、変更前の日付の書きかけを消す(FR-005)。変更後の日付に空でない書きかけが既にある場合は、置き換える前に確認する。取り消したら日付を元に戻す。
- **Rationale**: 日付の変更は「いま書いている絵日記の日付を変える」操作である。別の日付の書きかけを黙って上書きすると内容が失われる。憲章 IV の「取り消せない操作には実行前の確認」に従い、既存の画面と同じ `window.confirm` で確認する。
- **Alternatives considered**: 日付を変えたら、変更後の日付の書きかけを読み込み直す: 入力中の内容が画面から消え、利用者の意図に合わない。

## 7. ほかの日付の書きかけの案内

- **Decision**: 新規の記入画面で、画面の日付以外の空でない書きかけを、新しい日付順に一覧する。各項目は `/diaries/new?date=<date>` へのリンクとする。`draft-store.ts` に `listNewDraftDates(user)` を加え、キーの範囲(`IDBKeyRange.bound`)で利用者の新規の書きかけだけを読む。
- **Rationale**: FR-006、US3。書きかけを日付ごとに分けても、利用者が書いた内容を見失わない。カレンダーから開いた画面でも同じ案内を出す(条件を「書く」だけに絞る理由がなく、単純になる)。
- **表示**: ページ(カード)の上、見出しの下に「書きかけの絵日記があります」と、日付(`formatJapaneseDate`)のリンクを並べる。002 のページ構成(カードの中)は変えない。

## 8. 修正前の書きかけの引き継ぎ

- **Decision**: 記入画面を開いたときに、古いキー `"<user>:new"` が残っていれば、1つのトランザクションで次を行う。
  - 空でなければ `"<user>:new:<書きかけの日付>"` へ移す(移動先に既にあれば、移動先を残す)。
  - 古いキーを消す。
- **Rationale**: FR-008、憲章 IV(保存形式の変更にはデータを失わない移行とそのテストを伴う)。古いキーは修正前にしか作られないため、移動先と重なるのは同じ画面を2つのタブで開いていた場合などに限られる。その場合は、新しい形式の書きかけ(修正後に書いた内容)を残す。
- **Alternatives considered**: IndexedDB のバージョンを上げて `onupgradeneeded` で移す: キーの形の変更にはデータベースの構造の変更が要らない。必要以上に大きな仕組みになる。

## 9. テストの変更(憲章 V)

- 先に、不具合を再現して失敗するテストを加える。
  - 単体: 11月8日の書きかけがある状態で「書く」を開くと、日付欄が今日になる。
  - 単体: 空の状態で開いただけでは書きかけが保持されない。
  - E2E: Playwright の `page.clock` で 11月8日に「書く」を開いて閉じ、11月22日に再び開くと「11月 22日(日)」が表示される。
- 既存のテストの変更と理由:
  - `restores a draft saved before the tab was closed`(単体): 書きかけの日付を今日に変え、別の日付の書きかけは戻らず案内に出ることを確かめるテストを別に加える。理由は、別の日付の書きかけが戻る動きが、本仕様の FR-001 と FR-003 に反するためである。
  - `draft-store.test.ts`: キーの形の変更に合わせて、新規の書きかけを日付ごとの関数で扱うように書き換える。期待する動き(画像を含む保存と復元、利用者ごとの分離、保存後とログアウト時の消去)は弱めない。

## 10. 扱うデータと脅威(憲章 I)

- **扱うデータ**: 記入中の文章、天気、画像、日付。保持場所は利用者の端末の IndexedDB のみで、今回の変更で場所は変わらない。
- **脅威と対策**:
  - URL の `date` に不正な値を入れる: `diaryDateSchema` で検証し、不正なら今日にする。日付はリンクの URL と表示にしか使わず、React の通常の描画で表示する。
  - 端末の共有で他人の書きかけが見える: キーに利用者を含め、案内には自分の書きかけだけを出す。ログアウト時の全消去(001 FR-017)は変えない。
  - 書きかけが日付ごとに増えて端末に残る: 空の書きかけは保持せず、保存の成功時に消去する。ログアウト時に全部消える。
