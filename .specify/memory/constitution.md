# diary-log Constitution

## Core Principles

### I. セキュリティ最優先 (NON-NEGOTIABLE)

- セキュリティは最優先事項であり、機能、利便性、開発速度、または他の原則と衝突する場合は
  セキュリティを優先しなければならない(MUST)。
- インポートファイルや URL パラメーターなど外部から入る値は信頼せず、使用前に検証しなければ
  ならない(MUST)。
- 日記の内容を画面に表示する際は、スクリプト実行につながらないよう無害化しなければならない
  (MUST)。
- Content Security Policy を設定し、インラインスクリプトと外部オリジンへの接続を既定で禁止
  しなければならない(MUST)。
- 秘密情報をリポジトリに含めてはならない(MUST NOT)。
- 依存関係に既知の脆弱性がある状態で push してはならない(MUST NOT)。
- 各機能の計画では、扱うデータ、想定される脅威、およびその対策を明記しなければならない(MUST)。

**理由**: 日記には極めて機微な内容が含まれ、一度漏えいした情報は取り戻せない。

### II. ローカルファースト (NON-NEGOTIABLE)

- 日記データは利用者の端末内のブラウザストレージに保存し、これを唯一の正本としなければ
  ならない(MUST)。
- 日記の作成・閲覧・編集・削除・検索は、ネットワーク接続なしで動作しなければならない(MUST)。
- 日記の利用に、アカウント登録やログインを要求してはならない(MUST NOT)。
- 日記データを保持するサーバーを導入する変更は、本憲章の MAJOR 改定なしに行ってはならない
  (MUST NOT)。

**理由**: 日記は極めて私的な記録であり、サービスの継続や接続状況に左右されず、利用者自身の
手元で完結している必要がある。

### III. プライバシー保護 (NON-NEGOTIABLE)

- 日記の本文・タイトル・タグ・日付などの内容を、利用者の明示的な操作なしに端末外へ送信して
  はならない(MUST NOT)。
- アナリティクス、広告、トラッキング、および外部へのエラー送信を組み込んではならない
  (MUST NOT)。
- 日記の内容をログやエラーメッセージに出力してはならない(MUST NOT)。
- 実行時に必要なスクリプト、スタイル、フォントは、アプリと同じ配信元から提供しなければならない
  (MUST)。

**理由**: 内容が端末外へ出ない構成であれば、プライバシーを運用上の約束ではなく設計によって
保証できる。

### IV. データの保全と可搬性

- 入力中の内容は、保存操作の失敗やタブの終了によって失われないよう保護しなければならない
  (MUST)。
- 保存に失敗した場合は、利用者に明確に通知し、入力内容を保持しなければならない(MUST)。
- 日記の全データは、公開仕様の形式でいつでもエクスポートでき、同じ形式からインポートでき
  なければならない(MUST)。
- 保存形式の変更には、既存データを失わないマイグレーションとそのテストを伴わなければならない
  (MUST)。
- 削除など取り消せない操作には、実行前の確認を設けなければならない(MUST)。

**理由**: 日記の価値は長年の蓄積にあり、失われたデータは再現できない。またブラウザストレージ
は消去される可能性があるため、利用者が自分でバックアップできる手段が不可欠である。

### V. テスト駆動開発 (NON-NEGOTIABLE)

- 動作を追加・変更するコードは、TDD で開発しなければならない(MUST)。先にテストを書き、失敗を
  確認してから実装し、すべてのテストの成功後にリファクタリングする。
- 不具合の修正では、その不具合を再現して失敗するテストを先に追加しなければならない(MUST)。
- テストを通すために、テストの削除、無効化、または期待値の緩和をしてはならない(MUST NOT)。
  仕様変更によりテストを変更する場合は、その理由を記録しなければならない(MUST)。
- 動作を変えない文書、設定、および見た目のみの調整は、TDD の対象外とする。

**理由**: 先にテストを書くことで要求を実行可能な形で確定でき、データを扱うコードの不具合を
利用者に届く前に検出できる。

### VI. シンプルさ(KISS・YAGNI)

- 要件を満たす最も単純な設計を選択しなければならない(MUST)。
- 現在の仕様で必要な機能だけを実装し、将来の仮定に基づく抽象化や設定項目を追加してはならない
  (MUST NOT)。
- 新しい実行時依存を追加する場合は、必要な理由と標準機能では不足する理由を ADR に記録しな
  ければならない(MUST)。
- 記録することが主目的であるため、日記を書き始めるまでの操作は最小限に保つ(SHOULD)。

**理由**: 依存と複雑さが小さいほど、長期にわたる保守が容易になり、データへのリスクも小さくなる。

### VII. DRY

- 同じ知識やビジネスルールは、コード内の一箇所でのみ定義しなければならない(MUST)。
- 重複を検出した場合は、同じ変更の中で解消するか、解消しない理由を記録しなければならない(MUST)。
- 偶然似ているだけで変更理由が異なるコードは、共通化してはならない(MUST NOT)。

**理由**: 知識の重複は修正漏れによる不整合を生む。一方、無理な共通化は原則 VI に反する複雑さを
生むため、対象はコードの見た目ではなく知識の重複とする。

### VIII. 明示的なエラー処理

- エラーを握りつぶしてはならない(MUST NOT)。捕捉したエラーは、処理するか呼び出し元へ伝播させ
  なければならない(MUST)。
- 既定値、代替処理、または空の結果でエラーを隠してはならない(MUST NOT)。
- フォールバックは、仕様に定義された場合にのみ実装でき、利用者への通知の要否を仕様に明記
  しなければならない(MUST)。
- 想定外のエラーは利用者に失敗として提示し、処理を続行してはならない(MUST NOT)。

**理由**: 隠されたエラーは、データの破損や消失に気付けない状態を生む。失敗は早期かつ明確に
表面化させる。

## Web プラットフォーム要件

- 対象は主要なモダンブラウザ(Chrome、Edge、Firefox、Safari)の最新安定版とする(MUST)。
- スマートフォンからデスクトップまでの画面幅で、横スクロールなしに利用できること(MUST)。
- 主要な操作はキーボードのみで実行できること(MUST)。アクセシビリティは WCAG 2.1 AA を
  目標とする(SHOULD)。
- 初回読み込み後は、再読み込みを含めてオフラインで起動できること(MUST)。
- 永続ストレージが利用できる環境では、ブラウザによる自動削除を避けるため永続化を要求する
  (SHOULD)。
- 具体的な技術スタックは本憲章では定めず、各機能の計画で原則 I〜VIII に照らして選定し、ADR に
  記録する。

## 開発ワークフロー

### 開発の流れ

- 機能開発は、仕様(spec)、計画(plan)、タスク(tasks)、実装の順に進める(MUST)。
- 計画段階で本憲章への適合を確認し、逸脱がある場合は理由と却下した代替案を計画に記録
  しなければならない(MUST)。
- 保存形式やデータ処理を変更する場合は、既存データを使った動作確認を行う(MUST)。

### 品質ゲート

- push の前に、次のすべてを実行し、問題がないことを確認しなければならない(MUST)。
  - すべての自動テストの成功
  - lint のエラーなし
  - 型検査を含む静的解析のエラーなし
  - 依存関係の脆弱性検査で既知の脆弱性なし
- いずれかが失敗した状態で push してはならない(MUST NOT)。
- lint や静的解析の指摘を抑制する場合は、対象を最小限にし、理由をコードに記載しなければ
  ならない(MUST)。

### ADR

- 次の判断を行う場合は、Architecture Decision Record(ADR)を `docs/adr/` に記録しなければ
  ならない(MUST)。
  - 技術スタックや実行時依存の選定
  - 保存形式やデータ構造の決定
  - セキュリティに関わる設計判断
  - 本憲章からの逸脱
- ADR には、背景、決定内容、検討した代替案、および影響を記載しなければならない(MUST)。
- 採択済みの ADR の決定は書き換えず、変更時は新しい ADR で置き換えなければならない(MUST)。

## Governance

- 本憲章は、プロジェクトの他のすべての開発慣行に優先する。
- 改定は `.specify/memory/constitution.md` への変更として行い、変更理由、バージョン更新、
  および必要な移行手順を記録しなければならない(MUST)。
- バージョンはセマンティックバージョニングに従う。
  - MAJOR: 後方互換性のない原則の削除または再定義
  - MINOR: 原則・セクションの追加、または指針の実質的な拡張
  - PATCH: 意味を変えない明確化、文言修正、誤字修正
- すべての計画および変更のレビューでは、本憲章への適合を確認しなければならない(MUST)。
- NON-NEGOTIABLE と記された原則(I、II、III、V)の緩和は、MAJOR 改定としてのみ行える。
